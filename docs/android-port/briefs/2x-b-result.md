## Rules that now match

Queued works are normalised on restore the way `ReadingQueueService.normalize` does, on both sides. A membership sets `isQueuedForLater`. A queued work whose EPUB is in the restore becomes `preserved`, and gains `preservedAt` only when the archive had none. Unknown metadata that still needs an AO3 refresh becomes `pending`. Works with no membership are left alone, so a pass-through preservation status is not rewritten and a queue-only work stays out of the library.

`lastMembershipChangedAt` is the newest of the queue clock and its membership clocks. Saved for Later is pinned at sort order `-1000` (new system queue, and `min` of an existing one). The next custom queue's sort is still `max + 1`, so a library that already has Saved for Later continues at `-999`. This is a one-time upsert in `ensureSavedForLaterQueue`, not a Room migration.

A work created by restore keeps `assetIdentifier` `<UUID>.epub`, using `UUID.uuidString`'s uppercase form. An existing local identifier is left as it is. Zip entry names stay lowercase.

New works, new collections, and a Saved for Later queue created by the restore keep the archived clock. See `docs/android-port/DECISIONS.md` (2026-10-03). Existing records still use `max`.

The cross-platform seed is already in that post-restore state: work 2 is queued, preserved, and `pending`, with `preservedAt` set so neither side stamps "now"; both queues store the membership clock they would derive; Saved for Later is `-1000`; both asset identifiers are the default `<UUID>.epub`. CryptoKit's Ed25519 `signature(for:)` is randomized, so the seed pins one valid signature from the all-zero test key instead of calling `sign` on every run.
