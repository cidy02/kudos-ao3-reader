# Brief 3ao result: what the reader's menu holds

**Landing note (Claude, 2026-10-05).** Landed as written, with one change: the pills take their
width from the row of round buttons, as on iOS, and an import with no link has only three of
them on Android (there is no file sharing yet), which was too narrow for the labels; the pills
now never go narrower than four buttons' width. Gate green (1,482 tests). Seen on the
emulator: the menu of an imported work and of an AO3 work (Comments, Share and Give kudos
appear for the second). The brief was wrong that Android lacked Comments and Kudos. What a
reader will notice: **Mark finished is no longer in the reader's menu** (it is on the work's
page, as on iOS); Share is absent for an import with no link (it used to share only the title);
Read aloud and Add bookmark are greyed out when they cannot work; the comments page's error
messages are iOS's. Not exercised: kudos, comments and share taps (kudos is a write to AO3 and
the demo was not asked to answer it here).

The iOS reference is `/Users/cidy02/kudos-ios-polish/kudos-ao3-reader/Features/ReaderReadium/ReadiumReaderView.swift`, especially `fanPills`, `fanRoundActions`, `shareURL`, `currentAO3Chapter`, and `giveKudos`; rendering is `ReaderFanMenu.swift`. Except the conditions explicitly listed above, menu availability is independent of signed-in state, selection, local Finished, author completion, and AO3 restriction. A converted import with a recovered AO3 identity can have both AO3 actions and original-file actions.

The earlier-look claims in the brief are stale: **Android already has Comments and Kudos**. iOS code wins: Original is an icon button, and Rebuild from Original is an additional conditional pill. “One request per tap” means one write dispatch: both existing platforms prepare it with a CSRF GET before the single POST. Neither current Work Detail nor iOS reader asks for pre-kudos confirmation; the tap expresses intent and the result confirms it.

Android-only actions: iOS Highlight/Add Note live in `ReadiumBook.selectionEditingActions`, dispatched to `createAnnotationFromSelection`. Android `ReadiumNavigatorHost` does not add those text-selection actions; the two fan pills are its only creation entry points, so they must stay after the iOS pills. iOS manually finishes through Work Detail (`WorkDetailFactsSections`/`toggleFinished`) and automatically finishes complete works at the trailing edge (`openBook` → `book.onReachedPublicationEnd`); Android has Work Detail `WorkDetailPageActions`/`onToggleFinished` and `ReaderViewModel.maybeAutoFinish`. Its fan's Mark finished was removed; title-tap opens the existing Work Detail over the reader and Back returns to reading. No new end-of-work page is needed.

Changes written (Android only, uncommitted on `android/agent-codex-3ao`):

- `reader/ReaderFanMenu.kt` now owns the testable pill-content builder and kudos configuration. Pill order: **Contents → Bookmarks & Highlights → Find in Work → Comments (AO3 identity only) → Themes & Settings → Highlight selection → Add note to selection**. No Mark finished pill. All existing glass, sizing, animation, pill and icon-button composables are unchanged. Existing Material icons remain; no new glyph artwork or menu redraw.
- `reader/ReaderScreen.kt` still opens the same Contents/search/display sheets, sends Comments through the existing `onOpenComments` callback to `Routes.comments`, and calls the same selection/dialog/annotation entry points. Its Contents percentage now rounds total progression and shows 0% when known. `ReaderSection.commentsChapter` ports iOS's existing mapping over Android's existing normalized sections: front matter → 1, chapter → story chapter, back matter → preceding chapter, no position/sections → All. `EndOfWorkActions.forWork` now prefers the already-stored `SavedWork.ao3WorkID`, with the existing `WorkTags` source-URL fallback, matching iOS. No new metadata requests.
- The round row remains in iOS's available order: **Share (link available) → Give kudos (AO3 only) → Read aloud → Lock rotation → Add bookmark**. Original is omitted for the missing capability explained below. Share selects AO3 first, then an HTTP source link, and calls Work Detail's existing `shareWork` (only its visibility changed from private to internal). Title-only sharing for a linkless import was removed: the iOS action shares the EPUB in that state, which Android cannot currently do. Work Detail's existing title/source sharing remains there.
- `ReaderViewModel.giveKudos` keeps `AO3WriteRepository.giveKudos`, exactly the Work Detail write entry point. It sets an in-flight flag **before** coroutine launch, rejects in-flight/already-given calls, persists successful or already-left results through the existing `ReaderRepository.markKudosGiven`, and updates the in-session work so the heart becomes filled/disabled immediately. A failure clears the in-flight flag, preserves the work and allows a later explicit tap; no retry is introduced. Existing Snackbar result handling stays. iOS has no pre-tap kudos confirmation, and neither does Android Work Detail; no dialog was added. The CSRF GET and single POST are entirely owned by the unchanged existing repository.
- Signed-out kudos says **“Log in to AO3 first.”** Restricted/missing/rate-limited/HTTP kudos failures use iOS reader words through `readerKudosErrorMessage`. `comments/CommentsViewModel.kt` uses iOS comments-screen login/restricted/missing/offline/rate-limit words on the existing load-failure path (`commentsReadErrorMessage`); this is copy on the shared destination, not a new reader comments implementation. No request behavior changed.
- Read aloud is disabled without Readium's existing content service (`ReaderContentText.isAvailable`). Its start no longer substitutes title/TOC speech for absent story text; the existing `ReaderSpeechController.startReading`/`stop`, playing-or-paused emphasis and settings long press remain. Bookmark is disabled until a live compatible locator has an actual `locations.position`; its emphasized state now follows the existing `AnnotationRepository.removeBookmarkNear` threshold rather than the whole spine.

Capabilities deliberately omitted / remaining fidelity limits:

| Capability | Why omitted or limited / what it would take |
|---|---|
| Original icon | No Android original-viewing entry point exists. `WorkFileStore.originalFile` is storage access only; Work Detail has rebuild controls, no Original viewer. Needs an original-preview/open flow with MIME-aware URI grants (or an internal viewer), first added as its own feature and then called by this menu. The APK installer's FileProvider path is not an original-viewing entry point. |
| Rebuild pill | The rebuild operation exists (`WorkImporter.rebuildFromOriginal`) and remains on Work Detail / Home menus. The **iOS stale-only condition** does not: `canRebuildFromOriginal` checks existence only; conversion sidecars are preserved as bytes, not interpreted against an Android converter revision. Showing every original would disagree with iOS. Needs a real converter-revision/staleness capability before wiring that existing rebuild call into the fan. No converter/versioning feature was built here. |
| Share an EPUB with no source link | No existing work/reader file-sharing entry point. Needs a shareable EPUB URI and grants/MIME-aware sharing, then the fan can use it as iOS's final fallback. No title-only surrogate retained. |
| Exact bookmark identity | iOS toggles by publication-wide `Locator.locations.position` equality. Android's existing toggle/remove entry point is a same-spine, ±0.02 progression match. The fan now reflects that existing toggle honestly and requires a position before enabling it. Exact identity needs a separate change to the annotation toggle entry point; its existing annotation matching/persistence behavior is unchanged. |
| Expired session vs signed out | Android returns the same `AuthenticationRequired` error for both. The reader uses the required signed-out iOS wording; iOS distinguishes an expired authenticated session (“Your AO3 session expired. Please log in again.”). Exact distinction needs auth-error information not currently available to this callback. No auth feature was added. |
| Speech settings / engine | The existing Android hold opens its display sheet, which contains Read Aloud controls; iOS uses a dedicated speech sheet. Android also keeps its existing missing-model/install handling. No new speech destination/engine was built. |
| Selection pills | Kept intentionally, with their existing labels, after the iOS core pills. iOS's Highlight/Add Note are in the native text-selection menu. Android's Contents Add Note creates a chapter-position note and edits existing marks, not a note anchored to a selected passage; removing the selection pills would lose passage creation. Needs Android selection-menu integration before these pills can go. |
