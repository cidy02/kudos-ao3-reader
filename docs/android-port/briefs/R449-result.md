# R449 — adversarial review of T-449

What this change does: `97187d9a` holds a Readium locator across a size change, restores it after 220 ms of quiet, and remeasures the chapter's pages. It also pads the reader and its controls by the host's side safe areas.

Target: `/Users/cidy02/kudos-ios-polish`, commit `97187d9ae8dd09835f6bbf81549c20422cf2ce88`. References below are at that commit. Review complete: **three P1 findings and one P2 finding**. These are source-traced failure paths; none was reproduced on a device in this read-only review.

## Must fix

1. **P1 — An intentional same-chapter seek is discarded and restored away.** `kudos-ao3-reader/Features/ReaderReadium/ReadiumBook.swift:212–214, 230–234, 730–735`.
   - **Sequence:** With a measured chapter at passage A, resize. Before the restore completes, jump to a different bookmark in that chapter, choose that chapter's start in Contents, or let an already-running scrub seek reach B. Those commands still call the navigator (`ReadiumReaderView.swift:845–847, 1635, 1900`; `ReadiumBook.swift:475, 646–653`).
   - **Result:** The same-href gate drops B before updating `currentLocator` or notifying persistence. The resize task subsequently jumps to A. Closing/backgrounding meanwhile flushes A (`ReadiumReaderView.swift:913–934`), losing the user's selected resume position. Read Aloud's same-chapter follow/restart has the same conflict (`ReadiumReaderView.swift:338–342, 1732–1735`).
   - **Smallest fix:** Explicit navigation must supersede and cancel the resize restore before dispatch, including scrub and speech paths; preserve the gate only for unsolicited reflow callbacks. Ensure cancellation also restarts page measurement and does not let an already-issued restore win afterward.
   - **Evidence:** Confirmed control-flow defect. No runtime reproduction performed. The new resize test does not execute a real restore: `GeometryTestNavigator` is only passed as a delegate argument, and `book.navigator` remains nil (`KudosTests/ReadiumReaderTests.swift:435–466, 564–570`).

2. **P1 — Resizing while a chosen chapter loads restores the previous chapter.** `kudos-ao3-reader/Features/ReaderReadium/ReadiumBook.swift:212–214, 230–234, 730–735`.
   - **Sequence:** Read chapter A until its page count is ready. Use Contents to jump to a distant, not-yet-loaded chapter B. While B is still loading and before its first locator callback, change size. `currentLocator` still names A, and `hasMeasuredPageBox` remains true across chapter changes. The resize captures A; after 220 ms it issues a jump back to A.
   - **Result:** B never gets to deliver the different-href callback that would release the hold. The reader returns to the old chapter, and close/background flush saves A. The comment that a real chapter navigation wins is only true when its callback beats the restore.
   - **Evidence:** Readium's `EPUBNavigatorViewController.go(to:)` returns after `PaginationView.goToIndex` and sets the state idle (`EPUBNavigatorViewController.swift:728–745`). A distant jump starts page loading without waiting for it (`PaginationView.swift:393–423, 244–272`); the location update waits for loading/progression notifications (`EPUBNavigatorViewController.swift:1229–1232, 1276–1281`). Thus a loading B can coexist with an accepted restore to A. These are the pinned SDK's paths, not a simulated timing assumption.
   - **Smallest fix:** Track a pending intentional navigation target before issuing the command. A resize during that navigation must preserve B's target, or defer its hold until B settles; it must not snapshot A. Cancelling only when B's delegate callback arrives is too late.

3. **P1 — The held locator preserves a pixel fraction, which can point at another passage after reflow.** `kudos-ao3-reader/Features/ReaderReadium/ReadiumBook.swift:214, 231`.
   - **Sequence:** In a scrolled EPUB chapter, put a fixed-height illustration/block before the current paragraph and wrapping prose after it. For example, the block is 2,000 px tall and the prose 18,000 px tall; the paragraph just below the block is at progression 0.10. Widen the reader so the prose takes 9,000 px while the block stays 2,000 px. The task restores 0.10 of the new 11,000 px: offset 1,100, now 900 px before the paragraph.
   - **Result:** The original passage is lost even without a concurrent gesture. Subsequent location callbacks and close/reopen retain the numeric fraction for the wrong passage. This is especially exposed by scrolled mode, which does not merely round to a containing page.
   - **Evidence:** Normal EPUB position locators have no passage text or fragment (`EPUBPositionsService.swift:147–157`); the SDK reports their progression from the viewport (`EPUBViewportAndLocationCalculator.swift:94–102`). `go(to:)` therefore uses `scrollToProgression`, and JavaScript multiplies that number by the *new* `scrollHeight` (`EPUBReflowableSpreadView.swift:293–312`; `Scripts/src/utils.js:180–202`). The new test supplies an artificial `fragments: ["passage"]` (`KudosTests/ReadiumReaderTests.swift:441–444`), unlike those ordinary callbacks.
   - **Smallest fix:** Preserve a content anchor before reflow, using the existing `navigator.firstVisibleElementLocator()` API, and restore that anchor. Keep progression as a fallback when no content anchor can be obtained; do not describe that fallback as exact position preservation.

4. **P2 — A failed reload can leave the hold waiting forever; cancelling the task does not cancel the SDK wait.** `kudos-ao3-reader/Features/ReaderReadium/ReadiumBook.swift:220–245, 249–252`.
   - **Sequence:** After a measured chapter, rotate so Readium reloads its spreads. Its replacement document has not finished loading when the 220 ms task calls `go(to:)`. Let that WebKit load fail before sending `spreadLoaded`. Readium accepts the jump but suspends its completion on a checked continuation. Now close the reader.
   - **Result:** While the reader remains open, the hold never clears and the page bar cannot be measured (`ReadiumBook.swift:881`). On close, `cancelPageBoxRemeasure()` clears the stored handle/hold but cannot unwind the suspended `go`; the task already holds `self` strongly after line 222. The book/navigator remain retained by the unfinished restore. This needs a failed/stalled load; ordinary successful restores do return.
   - **Evidence:** The pinned SDK's `EPUBReflowableSpreadView.go(to:)` waits for document load via `waitGoToCompletion` (`EPUBReflowableSpreadView.swift:229–263`). That continuation has no cancellation handler. `EPUBSpreadView.webView(_:didFail:withError:)` only logs (`EPUBSpreadView.swift:643–645`); removing the reader from its window cancels `PaginationView.loadPagesTask` but does not remove/clear its nested spread views (`PaginationView.swift:172–179`). There is no app-side timeout around the awaited jump. Runtime fault injection was not performed.
   - **Smallest fix:** Make the restore's pending-load completion cancellation/failure-aware, so failure or reader teardown resumes it; bound the retry path and retain the last good locator on failure. Check cancellation immediately after `go` returns, before `markFirstPagePresentedIfNeeded`. A timeout that merely calls `Task.cancel()` on this same SDK await is insufficient.

## Other requested checks

- **Rapid fold/unfold/fold within 220 ms:** Before any restore has started, each geometry report cancels the previous sleeper and keeps the original held locator. No separate overwrite was found on that quiet-period-only path. Once a navigation or SDK await overlaps, findings 1, 2, and 4 apply. A cancelled successful `go` also calls `markFirstPagePresentedIfNeeded` before checking cancellation (`ReadiumBook.swift:231–241`); the fix for 4 must fence that stale side effect.
- **Contents, bookmarks, scrub, Read Aloud:** Traced through the actual command paths, not just the delegate. Findings 1 and 2 apply. Scrub release has a position-list fallback when the resize clears the page bar (`ReadiumReaderView.swift:1877–1900`), so disabling the slider during resize does not eliminate the overlap. Speech continues to issue chapter-local follows during a hold (`ReadiumReaderView.swift:338–342`).
- **Close/reopen and background/foreground:** `flushProgress` uses the book's held `currentLocator`, so it does not itself substitute an untrusted live SDK locator (`ReadiumReaderView.swift:913–934`). It does save the obsolete/wrong passage in findings 1–3. Explicit Close latches ingestion; `onDisappear` cancels the resize job (`ReadiumReaderView.swift:893–907, 423–447`). Background/inactive flushes do not suspend the resize job (`ReadiumReaderView.swift:405–421`); background WebKit timing with ongoing audio was not exercised.
- **Side padding versus vertical freeze:** Side padding wraps the navigator and all chrome together (`ReadiumReaderView.swift:975–987`); `navigatorContentInset` uses the full host height and only vertical insets (`ReadiumBook.swift:1261–1280`). Left/right-to-leading/trailing mapping is consistent in both directions (`ReaderPageBoxGeometry.swift:10–14`). A top-only change to zero is frozen at unchanged size/insets (`ReaderPageBoxGeometry.swift:26–35`). No additional confirmed side/vertical disagreement. First-show status-bar transitions from an initially zero top inset and sheet presentation transforms still need visual checks.
- **Ordinary portrait iPhone:** No additional confirmed regression when size and meaningful safe insets stay unchanged. The host's equality guard prevents scheduling work in that steady state (`ReadiumBook.swift:203–209`), and ordinary ready-state page turns keep the existing digit-refresh path (`ReadiumBook.swift:748–755`). This is source verification, not a visual-baseline claim.
- **DEBUG hook:** No release-build reachability found. The entire `DemoLibrary.swift` file, including `runRotations`, is inside `#if DEBUG` (line 1); the call is also inside `#if DEBUG` and `#if os(iOS)` (`ContentView.swift:66–77`). No signing, bundle, or release-configuration changes are in this commit.
- **Test coverage:** The added fake only drives delegate input; it is never installed as the owned navigator. Consequently, the tests skip the restore loop and cannot verify accepted/rejected jumps, load completion, cancellation during an SDK await, or persistence after a competing navigation. Add a controllable navigation seam and regression cases for findings 1–4 when fixing them; manually prove the anchor with a mixed-layout chapter.

**Verdict: fix findings 1–4 before shipping the resize-preservation claim.**
