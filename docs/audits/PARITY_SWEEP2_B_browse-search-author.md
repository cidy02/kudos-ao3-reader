| Finding | Technical | Plain English | Confidence |
|---|---|---|---|
| Concurrent Search/Browse/Author loads have no generation token — older responses can overwrite newer ones | `SearchScreen.runSearch` / `retry` (`SearchScreen.kt:99–127`), `FandomWorksScreen.load` (`FandomWorksScreen.kt:49–56`), `AuthorWorksScreen.load` (`AuthorWorksScreen.kt:56–63`), and `FandomListScreen.load` (`FandomListScreen.kt:55–65`) each do `scope.launch { … state = … }` with no cancel of an in-flight job and no `loadToken`/generation guard. iOS Search uses an explicit `loadToken` so a superseded fetch cannot re-apply (`SearchView.swift` ~714–735); Fandom works only sets loading when `results.isEmpty` and replaces results on the same path. On Android, rapid Search → page change, double-tap Next, or Search then Retry can complete out of order and leave the UI on the wrong page/filter set. | If you hit Search or flip pages quickly, the app can briefly show an older page of results after a newer request has already started — or land you on the wrong page after you thought you’d moved on. | high |
| Pagination / re-search always blanks the list into a full-screen Loading state | Every load path sets `state = …Loading` before the network call (`SearchScreen.kt:106,121`; `FandomWorksScreen.kt:50`; `AuthorWorksScreen.kt:57`; `FandomListScreen.kt:56`), and the `when` branches replace the whole results UI with `LoadingStateCard` (`FandomWorksScreen.kt:74`, same pattern elsewhere). iOS FandomWorks only enters loading when `results.isEmpty` (`NativeBrowseView.swift` ~180–181) and Search’s `loadPage` intentionally keeps the previous page visible while the next loads (`SearchView.swift` ~703–711). Android therefore tears down the list (and its scroll position) on every page flip. | Tapping Next/Previous on Search, a fandom’s works, or an author’s works makes the whole list disappear into a spinner, then rebuilds from scratch — you lose your place and can’t scan the previous page while waiting. On iPhone the old page stays up until the new one arrives. | high |
| Inline Sort control updates filters but never re-runs the search (and pagination then uses the new sort mid-stream) | `SearchControlsRow`’s sort menu only calls `onSortSelected` → `filters = filters.copy(sort = it)` (`SearchScreen.kt:207,446–459`) with no `runSearch()`. Visible results stay bound to the previous `SearchUiState.Results`. If the user then taps Next/Previous, `onPage = { runSearch(it) }` (`SearchScreen.kt:260`) uses the *current* `filters` (new sort) at the *current* page index, so they jump to page N of a different ordering without ever loading page 1 of that sort. iOS keeps sort inside `AO3FilterPanel` and only re-queries on Apply / `runSearch()`. | Changing “Sort: …” on the Search screen looks like it took effect (the label and chips update), but the work list stays in the old order until you manually press Search. If you change sort and then press Next, you skip into the middle of a differently sorted result set. | high |
| Browse category enrichment re-scrapes every media fandom index each session — no disk-backed catalog | `BrowseScreen` starts empty `fandomLists` and on every `load()` clears them, then `prefetchFandomLists` GETs each category’s `/media/…/fandoms` with concurrency 2 (`BrowseScreen.kt:71–89,167–190`). There is no Android equivalent of iOS `FandomCatalog` + `FandomCatalogCache` (on-disk, stale-while-revalidate, instant counts on relaunch; `FandomCatalog.swift` header + `warmCache`). Comment at `BrowseScreen.kt:163–164` even notes “in-memory only.” | Every time you open Browse, the app re-downloads the huge fandom indexes for every media category just to fill in “N fandoms / ~M works / recently read.” On iPhone those counts appear instantly from a local cache and only refresh in the background. Android is slower to enrich cards and hits AO3 harder on each visit. | medium |
| Category card stats are derived on the composition/main path when large fandom lists land | `BrowseScreen` computes `CategoryStatsCalculator.stats(...)` inside `remember(...)` during composition for each category (`BrowseScreen.kt:141–147`). `stats()` builds a lowercased name set from the full fandom list (tens of thousands for big media categories), scans the entire library for saved count, and sorts read works by `dateAdded` (`CategoryStats.kt:40–74`). iOS deliberately moved the same work off the main actor with a 150 ms debounce + `Task.detached` (`MediaBrowserView.swift` `recomputeStats` / `computeStats`) after main-thread rebuilds spiked CPU. Android re-runs this as each prefetched list arrives (map updates → recomposition). Distinct from the already-documented fandom *filter* keystroke jank on `FandomListScreen`. | After Browse’s categories load, the cards can hitch or freeze while “Counting fandoms…” fills in — especially for TV Shows / Anime — because the phone is scanning multi-thousand fandom lists against your library on the UI thread. iOS already fixed this class of stall. | medium |
| Empty search/browse/author page UI drops pagination controls, so a blank page has no Previous | In `FandomWorksScreen` / `AuthorWorksScreen` / `SearchScreen`, a successful load with `works.isEmpty()` renders only `EmptyStateCard` and **does not** include `PaginationRow` / `SearchResultsList` paging (`FandomWorksScreen.kt:77–81`; `AuthorWorksScreen.kt:88–92`; `SearchScreen.kt:251–255`). Previous/Next exist only in the non-empty branch. If AO3 returns an empty page while `totalPages` still allows navigation (over-filtered fandom edge cases once filters land, bad page index, or transient empty), the user cannot page back from that empty state. iOS keeps a stable pagination chrome path and empty overlays separately (`NativeBrowseView` / `SearchView` status overlays). | If a works page comes back empty, Android shows “No works found” with no Previous/Next — you may have to leave the screen entirely instead of stepping back to the last page that had results. | medium |
