# Parity Sweep 2A — Home / Library / Queues / Stats / Collections / Recently Deleted

**NEW findings only:** **10**

**Scope:** Android `home/` + `library/` (Library, Reading Queues, Statistics, Collections, Recently Deleted) vs iOS reference `.claude/worktrees/hig-review-reference/kudos-ao3-reader`.  
**Excluded by design:** anything already in [`ANDROID_PARITY_REPORT.md`](ANDROID_PARITY_REPORT.md) or [`ANDROID_PARITY_FINDINGS_VERIFIED.md`](ANDROID_PARITY_FINDINGS_VERIFIED.md) — fixed, confirmed-but-unfixed, refuted, or known/deferred gaps (queue soft-delete product path, `isSaved`-gates-Library, no See-All/filter UI, biometric reveal, non-EPUB import, queue-only/`markSaved`, subscriptions merge, WorkUpdateChecker failure backoff, stats `hasStarted`/`formatCompactNumber`, collection Add-Works / remove-confirm, sparse tests already listed, etc.).  
**Method:** verification-only re-read of current Android + pinned iOS reference; no source edits.

| Finding | Technical | Plain English | Confidence |
|---|---|---|---|
| Library **Reading History** uses the wrong membership predicate (Recently Opened clone, not freed-EPUB history) | Android `LibraryQuery.readingHistory` (`LibraryQuery.kt:130–134`) keeps any work with `lastReadDate != null`, sorted by last-read. That same stream is also what Home uses for **Recently Opened** (`HomeDashboard.kt:39`). iOS `LibrarySectionKind.history` (`LibrarySectionKind.swift:102–109`) is `!hasEPUB && !isQueuedForLater` — works whose EPUB was freed after finish (revisitable re-download shelf), with empty copy about “finish without saving.” Android empty copy still says “Nothing opened recently…” (`LibraryScreen.kt:591–592`), matching the wrong predicate. Unit test `readingHistoryUsesLastReadDateDescending` (`LibraryQueryTest.kt:167–171`) locks the Android definition in. Android *does* free EPUBs for unprotected finished works (`WorkRepository.setFinished`, `WorkRepository.kt:130–139`), so the iOS-shaped history set is reachable in principle, but the shelf never selects it. | On iPhone, **Reading History** is a distinct shelf of works the app stopped keeping offline (file freed; re-download to revisit). On Android that shelf is basically a second **Recently Opened** list of everything you’ve opened that still has a last-read date — including works still downloaded and still in Reading Now / Finished / Downloaded — so it doesn’t surface the same “history-only / re-download” works iOS does, and it duplicates Home’s Recently Opened semantics. | **High** |
| Library **Favorites** shelf is computed but never rendered | `LibraryQuery.buildState` builds `favorites` (`LibraryQuery.kt:37–40`); `LibraryUiState.favorites` and ViewModel reveal-mapping carry it (`LibraryModels.kt:65`, `LibraryViewModel.kt:72`). `LibraryScreen`’s shelf LazyColumn (`LibraryScreen.kt` ~501–600) wires Reading Now / Saved for Later / Finished / Queues / Collections / Downloaded / History only — **no** `LibraryCarousel` for `state.favorites`. iOS `LibraryView.dashboard` calls `localCarousel(.favorites)` after History (`LibraryView.swift:233–234`). | You can star works, and they show on **Home → Favorites**, but the Library dashboard never has a Favorites row at all. On iPhone the Library itself has that shelf so favorites are visible without leaving Library. | **High** |
| Library **Saved for Later** never merges AO3 **Marked for Later** remotes | Android Saved for Later carousel is only local `state.savedForLater` (`LibraryScreen.kt:517–530`), from `LibraryQuery.savedForLater` = `isSaved` (`LibraryQuery.kt:107–111`). No account-list fetch, no remote cards. iOS `savedForLaterCarousel` (`LibraryView.swift:289–319`) merges local section works with `filteredMarkedForLater` from `auth.accountWorks` Marked-for-Later (`loadMarkedForLater`, ~575+), rendering remote-only via `AO3WorkCoverCard` / `CanonicalWorkMerge.remoteOnly`. | If you’re signed into AO3 and have works Marked for Later on the site (not yet saved locally), iPhone shows them in Library’s Saved for Later shelf. Android only shows local “saved” works there; remote Marked-for-Later is only reachable via Account list shortcuts, not the Library shelf. | **High** |
| Reading **queue** UI counts and lists soft-deleted works | `ReadingQueueRepository.listWorks` (`ReadingQueueRepository.kt:40–50`) joins memberships to `workDao.getById` with **no** `isDeleted` filter (`WorkDao.getById` returns deleted rows). That list drives `QueueDetailScreen` rows and every “N works” count (`ReadingQueuesScreen.kt:46–50`, `LibraryViewModel.refreshQueues` `workCount = listWorks(...).size`, `LibraryViewModel.kt:288`). iOS `ReadingQueueService.orderedWorks` / `ReadingQueueCard.works` filter `!$0.isPendingDeletion` (`ReadingQueueService.swift:143–152`, `ReadingQueues.swift:29–33`). (Collections had the same class of bug; that path was fixed with `getWorksForCollection` / `getActiveWorkIdsForCollection` — queues were not.) | Delete a work into Recently Deleted and it can still appear as a normal item inside any reading queue it was in, and still inflate that queue’s work count on Library and the queues list — even though it’s gone from the rest of the library. | **High** |
| **Collection rename** missing | `CollectionDetailScreen` header trailing only offers Delete (`CollectionDetailScreen.kt:168–176`); `WorkRepository` has create/add/remove/soft-delete/restore but no rename API used by UI. iOS `CollectionDetailView` toolbar has Rename → alert → name mutation (`Collections.swift:219–239`). | Misspell a collection name or change your mind and Android’s only path is delete (Recently Deleted) and recreate — memberships aren’t renamed in place the way they are on iPhone. | **High** |
| Library multi-select bulk bar missing Save / Queue / Collection actions | `LibrarySelectionActionBar` (`LibraryScreen.kt:1370–1408`) only Favorite / Unfavorite / Finished / Unfinished / Remove / Cancel. Single-card menus still have Save, Add to Queue, Add to Collection (`LibraryScreen` context menu ~1011+). iOS `WorkBulkActionBar` also bulk Save/Unsave, Save for Later, Add to Queue, Add to Collection. | In multi-select you can favorite, mark finished, or delete many works, but you cannot bulk-queue or bulk-add-to-collection the way iPhone does — you have to do those one card at a time from the long-press menu. | **Medium** |
| Home has no multi-select / bulk actions | `HomeScreen` is shelves + open/reveal only; no selection mode, no bulk bar. iOS `HomeView` has `isSelecting` / `selection` / `WorkBulkActionBar` / Select in the more menu (`HomeView.swift:29–63, 140–158, 168–174`). | On Home, iPhone lets you select several local works and bulk-favorite/delete/etc. Android Home is open-only; bulk work only exists under Library. | **Medium** |
| Home / Library lack pull-to-refresh metadata refresh (and Home `refresh()` is unwired) | iOS Home `.refreshable { await refreshHome() }` runs `WorkMetadataRefresh.refresh(visibleHomeWorks)` + subscriptions (`HomeView.swift:117, 280–283`); Library dashboard `.refreshable { await refreshLibraryDashboard() }` does the same for visible works (`LibraryView.swift:241, 702–703`). Android `HomeViewModel.refresh()` (`HomeViewModel.kt:98–103`) re-runs update check + subscriptions but **`HomeScreen` never calls it** (no `PullToRefresh` / gesture). Library has no equivalent refresh path at all. (Work Detail’s missing refresh is already documented; this is Home/Library-specific.) | On iPhone, pull down on Home or Library to re-pull AO3 metadata for the works you’re looking at. On Android there’s no pull-to-refresh on those dashboards, and Home’s existing refresh method isn’t connected to the UI — only the automatic open-time update check / subscriptions load run. | **Medium** |
| Home Favorites / Recently Opened show progress bars; iOS does not | Android `HomeWorkCover` draws a progress bar whenever `footerOverride == null` (`HomeScreen.kt:349–350, 389–390`). Favorites and Recently Opened pass `footerFor = null` (`HomeScreen.kt:153, 170`). iOS `progress(_:_:)` returns a value only for `.readingNow` (`HomeView.swift:321–323`); favorites get no footer/progress; recentlyOpened is text footer only (`readingProgressLabel`). | On Android, Favorites and Recently Opened cards can show a full progress bar and “N% · Reading” like Continue Reading. On iPhone those rows stay cleaner (no bar; Recently Opened is text-only), so density/scan of those shelves differs. | **Medium** |
| Recently Deleted “days left” floors remaining time (iOS rounds up) | Android `expiryCaption` uses `ChronoUnit.DAYS.between(now, scheduled)` (`RecentlyDeletedScreen.kt:350–358`) — truncates partial days toward zero. iOS `daysRemaining` uses `(timeIntervalSinceNow / 86400).rounded(.up)` with a comment that an hour after delete should still read “90 days left,” not 89 (`RecentlyDeletedView.swift:161–167`). | Shortly after deleting something, Android can show one fewer day remaining than iPhone (e.g. 89 vs 90), which slightly understates the recovery window. | **Medium** |
