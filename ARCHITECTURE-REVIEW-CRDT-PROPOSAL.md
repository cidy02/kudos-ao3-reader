# Review: Cross-Platform Sync & Storage Architecture Proposal (CRDT / Sync Hubs)

Reviewed against the actual codebase at this worktree (`main`, commit `c878804`, plus the Android tree read from branch `android/mupdf-engine` at `cbbb804`, and the unmerged security branch `security-fixes/tombstone-trust` at `1369d4d`, all read via `git show`/`git ls-tree` without checking anything out or touching any other repo). This is a review only — nothing in the working tree was changed.

## Verdict up front

**Reject as submitted. Adopt zero of the sync-model changes; salvage two ideas (lazy hydration, an `iCloud` payload path) as narrowly-scoped follow-on work.** The proposal is solving a real problem (large-library / podfic storage math) with an architecture that would (a) take months, not "an implementation," to land, (b) throw away a security property this codebase just spent weeks establishing, and (c) wasn't checked against the data models it claims to simplify. Details below, directive by directive.

---

## 1. SwiftData/Room → shared cross-platform SQLite

**Ungrounded as "an implementation review."** This is not a layer swap; it's a rewrite of the persistence tier under a UI that queries it live.

What's actually there:
- iOS: `@Model` classes in `kudos-ao3-reader/Models/Models.swift` — `SavedWork` (704 lines total in the file; `SavedWork` alone runs from line 106 to 485, ~30 stored properties, 4 relationships, 10+ computed properties like `readingState`, `isProtected`, `needsAO3Refresh`), plus `Tag`, `Bookmark`, `CustomFont`, `WorkCollection`, `ReadingQueue`, `ReadingQueueMembership`, `SyncTombstone`.
- SwiftUI views read this store *live* via `@Query` — e.g. `kudos-ao3-reader/Features/Account/PrivacyDataView.swift:16` uses `@Query(filter: #Predicate<SavedWork> { !$0.hasEPUB && !$0.isQueuedForLater && !$0.isPendingDeletion })`. `@Query`/`#Predicate` is SwiftData-specific — it does not exist over a raw SQLite connection. Every `@Query` site in the app (dozens) would need to become an observed SQL query + a manual publish/subscribe layer, or the UI would need genuine rewriting, not just a "swap the layer underneath."
- Android: Room `@Entity`/`@Dao` in `android/app/src/main/java/io/github/cidy02/kudos/data/local/entity/*.kt` and `dao/*.kt` (`WorkEntity.kt`, `TagEntity.kt`, `CollectionEntity.kt`, `SyncTombstoneEntity.kt`, `WorkDao.kt`, etc.) — Room already sits on top of SQLite, so this side is a much smaller lift (arguably Room *is* "cross-platform SQLite" already, modulo API surface). Compose observes Room via `Flow`, which does have a rough SQLite-changefeed equivalent.
- Scope count: 55 iOS files reference `SavedWork` directly (`grep -rl SavedWork kudos-ao3-reader`), 43 Android files reference the Android `SavedWork` core model. App code (excl. tests) is ~42,400 lines of Swift; tests are another ~8,300 lines. None of that is Room-side, which is smaller but still real.

**Honest answer: this is a multi-month rewrite, not a "safe path."** The proposal doesn't name a migration strategy (dual-write period, view-compat shim, cutover order) at all — it states the destination ("migrate away from... SwiftData/Room... in favor of cross-platform SQLite") as if reachability were the only question. On the SwiftUI side specifically, swapping the persistence layer without an equivalent live-query mechanism means rewriting the observation model for every list/detail screen in the app, which is most of it.

## 2. Hydration state / `StorageState`

**Partially grounded — the proposal reinvents something 90% built, and understates how far it would still have to reach.**

`SavedWork.hasEPUB` already exists and is exactly the "record without a file" bit the proposal is asking for: `kudos-ao3-reader/Models/Models.swift:159` — `"Whether the EPUB is currently on disk. False = a history entry whose file was freed; revisiting re-downloads it."` It is load-bearing across the app, not a stub — real call sites include:
- `Services/WorkLifecycle.swift:48-56` (`freeEPUB` — deletes the file, flips `hasEPUB = false`)
- `Services/ReadingQueueService.swift`, `Services/WorkImporter.swift`, `Services/DownloadQueue.swift`, `Services/PersistenceSync.swift:291-295`, `Services/KudosBackup.swift` (backup encodes/restores it)
- UI: `Features/Library/LibrarySectionKind.swift:100-108` (History shelf = `!hasEPUB`), `Features/WorkDetail/WorkDetailView.swift:341-406` ("Read" vs "Download & Read" button label), `Features/Home/HomeCards.swift:97` (Offline badge), `Features/Account/PrivacyDataView.swift:16`
- Android equivalent: `WorkEntity.hasEpub: Boolean` in `android/app/src/main/java/io/github/cidy02/kudos/data/local/entity/WorkEntity.kt`, mapped from the shared `SavedWork.hasEpub` in `EntityMappers.kt`.

There's already a richer companion enum, `EPUBPreservationStatus` (`Models.swift:4-11`: `notPreserved / queued / preserving / preserved / failed / missingFile`), used by the Reading Queue "preserve permanently" feature (`ReadingQueueService.swift`).

So a `StorageState` enum (`local / icloudOffloaded / googleDriveOffloaded / downloading`) is not a new concept for this codebase — it's `hasEPUB` (bool) plus `epubPreservationStatus` (enum) generalized to name *which* remote holds the payload when absent. Real, non-trivial work still required: every one of the ~10 call sites above currently treats "not `hasEPUB`" as one case ("re-download from AO3"); they'd all need a second branch ("hydrate from cloud provider X" — different latency/progress/failure UX than a fresh AO3 download). That's a real but bounded change, unlike directive 1.

**The M4 lazy-EPUB point:** the task asked me to check for a "lazy EPUB reading" security fix. It exists, but **only on the unmerged `security-fixes/tombstone-trust` branch**, not on `main`/this worktree. On `main`, `.kudosbackup` restore fully materializes every EPUB into memory: `Services/KudosBackup.swift` reads `FileWrapper.regularFileContents` per work (`init(fileWrapper:)` around line 68, and the write path at line 937 does `Data(contentsOf: work.fileURL, options: .mappedIfSafe)` for every saved work). The security branch's review notes (`REVIEW-CLAUDE.md` on that branch, `FIX-2`) record that even the fix-in-progress is incomplete: *"directory import still materialises every EPUB (and the whole tree) after confirm... M4 is only actually fixed on the `.kudosbackup` ZIP path."* This directly corroborates the proposal's stated scale concern (10-50MB image-heavy EPUBs × thousands of works, 200GB of podfics) — the app's current backup/restore path really would choke on a large library, and the in-flight fix for that isn't finished or merged yet. This is the one place the proposal's problem statement is well-founded against real code, even though its proposed solution (CRDT + three cloud backends) is a wildly disproportionate answer to it.

## 3. EPUB storage / atomic-unit claim

**Grounded, and the proposal's own stated constraint matches the app exactly — no conflict.**

`Services/Storage.swift`:
- `worksDirectory` (`Storage.swift:36-41`) is the permanent home for EPUBs, one file per work, under `Application Support/Works/`.
- `defaultEPUBAssetIdentifier(for:)` (`Storage.swift:6-8`) names the file `"\(id.uuidString).epub"`.
- `workAssetURL`/`safeEPUBAssetIdentifier` (`Storage.swift:10-25`) resolve and sanitize that single-file path; there is no per-image or per-asset decomposition anywhere in the store.
- Import (`Services/WorkImporter.swift:18-60`) moves the whole downloaded file into place via `ReadingQueueService.replaceEPUB` and sets `hasEPUB = true` — the entire EPUB (images included, since AO3's own export embeds them) is the atomic on-disk unit, exactly as §2 of the proposal describes as non-negotiable.
- `.kudosbackup` (`KudosBackup.swift`) round-trips the same whole-file EPUB.

So directive 3 has no conflict to report: this is the one part of the proposal that is simply describing what already exists.

## 4. OAuth / Google Drive auth

**Grounded: there is no OAuth anywhere in this codebase, on either platform**, confirmed by a broad grep (`oauth|ASWebAuthenticationSession|SFSafariViewController|AppAuth` on iOS, `oauth|customtabs|appauth` on Android — only test/fixture files matched, all for AO3 comment/inbox parsing, unrelated). The only existing "auth" is `Services/AO3WebLoginCoordinator.swift`, which logs into **AO3 itself** via a `WKWebView` and scrapes/observes the session cookie (`AO3LoginPageObservation`, `AO3WebLoginCoordinator.swift:22-46`) — not an OAuth flow, since AO3 doesn't offer one. There is no reusable pattern here for Google Drive OAuth; it would be new, unrelated infrastructure.

Feasibility of what the proposal actually asks for (Google Drive REST + OAuth, "Kudos retains zero user credentials," no bloated SDK) is real but non-trivial: `ASWebAuthenticationSession` on iOS and Chrome Custom Tabs + a hand-rolled PKCE flow on Android are the right minimal choices and match how a privacy-conscious app should do it — but this is 100% new code, a new attack surface (redirect URI handling, token storage, refresh-token lifecycle), and a second, entirely different trust/consent model bolted onto an app whose whole pitch today is "no server, no accounts, files-on-disk." That's a legitimate product-direction question for the owner, not just an implementation detail.

## 5. Tag modeling vs. CRDT changeset size

**Grounded, and this is the sharpest concrete problem with the proposal — it did not check the data it's proposing to sync.**

Two different tag concepts exist, stored two different ways:

1. **User's own organizational tags** (`Tag` model, `Models.swift:488-495`) — genuinely relational: `@Model final class Tag { @Attribute(.unique) var name; var works: [SavedWork] }`, joined via `@Relationship(inverse: \Tag.works) var tags: [Tag]` on `SavedWork` (`Models.swift:317`). Android mirrors this with a real join table: `TagEntity` + `WorkTagCrossRef(workId, tagId)` in `android/.../data/local/entity/TagEntity.kt`. **This half would shape well into a CRDT** — small independent add/remove-edge rows are exactly what row-level CRDTs like cr-sqlite are good at.

2. **AO3's own intrinsic tags** — `workTags`, `workFandoms`, `workCharacters`, `workRelationships`, `workFreeforms`, `workWarnings`, `workCategories` — are **not relational at all**. They're `[String]` array columns stored directly on the `SavedWork`/`WorkEntity` row (`Models.swift:209-210, 245-252`; `WorkEntity.kt` same fields). On Android this is explicit and inspectable: `KudosTypeConverters.kt` serializes/deserializes the whole list as one JSON blob per column (`stringListToJson`/`jsonToStringList`) — Room (and SwiftData's own array storage, which does the same thing under the hood) treats the *entire tag list* as one opaque cell.

This is the real library content: an 18,000-work AO3 library's fandom/character/relationship/freeform taxonomy — potentially dozens of tags per work — lives in these blob columns, not the small user-tag join table. A row/column-level CRDT diffs at the *cell* granularity. Every background AO3 tag refresh (`SavedWork.needsAO3Refresh`, `Models.swift:288-307`, which runs per-work in the background specifically to backfill these fields) rewrites the whole blob for that work, which means **every single-tag change anywhere in an 18,000-work library becomes a full-column changeset write for that work**, not a delta — precisely the "large changeset" failure mode §4 of the proposal worries about, self-inflicted by not looking at the schema it proposes to CRDT-ify. Getting real benefit from a CRDT engine here would require first normalizing the AO3-intrinsic tag lists into join tables (a real, non-trivial migration on both platforms) — which the proposal doesn't mention needing at all.

## The gap the proposal doesn't address: CRDT-changeset-as-file vs. the tombstone trust model

This is real, it is serious, and — importantly — it's not hypothetical, because the app's own extremely careful attempt at exactly this problem still has known, unpatched holes. Confirmed by reading the actual code and the actual review history, not from prior context:

**What exists today (on `main`, this worktree):** `SyncTombstone` (`Models.swift:52-103`) is a plain, unsigned record — `id`, `recordID`, `recordTypeRaw`, `createdAt`, `lastModifiedAt`, `sourceURL`, `ao3WorkID`, `deletedOnDeviceID`, `deletionReason`. No `signerPublicKey`/`signature` fields. `Services/FolderSyncService.swift` round-trips these unsigned inside `KudosLibrary.kudosbackup` via `NSFileCoordinator`, and `KudosBackup.swift`'s `TombstoneIndex` (`KudosBackup.swift:1401+`) uses them to suppress resurrection of deliberately-deleted works — i.e., today, on `main`, the tombstone protocol already trusts whatever the sync folder hands it, unsigned. Android's `SyncTombstoneEntity` (`android/.../entity/SyncTombstoneEntity.kt`) is the same shape.

**What the owner actually built to fix that (unmerged):** branch `security-fixes/tombstone-trust` (worktree `/Users/cidy02/kudos-fix-tombstone`, tip `1369d4d`, 605 commits ahead of `main`, **not an ancestor of `main`** — confirmed via `git merge-base --is-ancestor`) adds exactly the primitive the proposal's "changeset resolved mathematically" claim needs and doesn't have: Ed25519-signed tombstones, a locked cross-platform signing contract (`PHASE2-CONTRACT.md`, commit `2f5579c`), a device trust store that a synced file is explicitly forbidden from writing to (`"A .kudosbackup must not write the trust store"`), and ~869 lines of new signing code plus 231 lines of new tests on iOS alone (`e4c9278`), mirrored on Android (`71f72fc`, `TombstoneSigning.kt`/`TombstoneTrustStore.kt`). This is precisely "trust, not just consistency" — the thing the proposal never mentions needing.

**And even that careful, adversarially-reviewed design has known, unpatched holes, confirmed still present at the branch's own "RC READY" tip:**
- **TOMB-1** (both platforms): the signed payload covers six fields (`recordType, ao3WorkID, canonicalSourceURL, recordID, deletedAt=createdAt, signerPublicKey` — `PHASE2-CONTRACT.md`), but `lastModifiedAt` — the *only* field that actually decides suppression (`tombstone.lastModifiedAt >= archivedModifiedAt`, `KudosBackup.swift`'s `TombstoneIndex.suppressesResurrection`) — is not one of the signed fields. `makeTombstone(from:)` copies it verbatim from the untrusted archive at `KudosBackup.swift:2140` (`tombstone.lastModifiedAt = archived.lastModifiedAt`) — confirmed still present, byte-for-byte the line the review flagged, unchanged between the review commit (`78b8bd2`) and the final "RC READY" commit (`1369d4d`; `git diff --stat 78b8bd2 1369d4d` touches only two Markdown files, zero code). An attacker with write access to one of the user's own `.kudosbackup` files can take a validly-signed tombstone, leave all six signed fields untouched (signature still verifies, signer still trusted), and set `lastModifiedAt` to a future date — permanently suppressing that work's resurrection with a **cryptographically valid** forgery.
- **TOMB-2** (Android only): the adopt loop keys its working map by the incoming row's own `id` (`BackupMergeService.kt`, `tombstonesById[BackupPaths.normalizeIdForComparison(incoming.id)] = incoming`), and `id` is **not a signed field**. An attacker can copy a validly-signed tombstone's six signed fields verbatim, but set `id` to match a different local tombstone that is currently suppressing a work the user deliberately deleted — the write silently overwrites (destroys) that local tombstone, resurrecting the deleted work. Confirmed present at the same tip, same "no code changed since the review" finding.

Both were flagged by the branch's own review (`REVIEW-CLAUDE.md`, commit `78b8bd2`: *"Two of these defeat the Phase 2 model and are the most serious findings of the entire cycle"*) and, as of the branch's last commit, **remain unfixed** — the branch went straight from "these are the two most serious findings" to a "RC READY — all gates green" handoff with no intervening code change to either file.

**What this means for the proposal:** the proposal's mechanism — "the engine generates a mathematical changeset... serialized into a JSON file, dropped into the user's cloud storage, and resolved mathematically on other devices — guaranteeing zero merge conflicts" — is a claim about **consistency** (any two replicas that see the same set of changesets converge to the same state), not about **authorization** (whether a given changeset was legitimately produced by a device the user trusts, and whether every field that affects trust decisions is actually covered by whatever proof of legitimacy exists). Consistency and trust are orthogonal properties; a CRDT guarantees the former and says nothing about the latter. A CRDT changeset for a delete is functionally a tombstone — an attacker who can write to the BYOS sync location can write a syntactically valid, mathematically-consistent changeset carrying a forged delete or a forged "never resurrect" marker, and every peer will faithfully, correctly, "zero-conflict" merge it in. The proposal shows no sign the author considered this distinction: there is no mention of signing, trust stores, device identity, or an adversarial sync-folder model anywhere in the document, and Option C (WebDAV to "user-provided Nextcloud or Synology NAS") is presented with even less implicit trust justification than iCloud/Drive — a self-hosted NAS is realistically the *most* likely of the three to have partial/compromised write access (shared household NAS, weak WebDAV creds, etc.), yet gets zero special treatment in the proposal.

Given that this exact problem — CRDT-style consistency across an untrusted sync channel — is what the owner's team spent weeks on, ran three adversarial review cycles against, and *still* shipped with two open, self-identified forgery holes on an unmerged branch, the proposal's implicit assumption of a trusted sync channel isn't a minor oversight to patch in later. It's the load-bearing wall the whole security effort was built around, and the proposal doesn't know it exists.

---

## Overall recommendation

**Reject the CRDT / Shared-Core / multi-Sync-Hub architecture as submitted.**

- Directive 1 confirms this is a multi-month, UI-touching rewrite dressed up as an "implementation," with no migration strategy offered.
- Directive 5 shows the proposal's own stated worry (large changesets) would be *worse*, not solved, against the actual tag schema, because the schema wasn't checked.
- The unaddressed section shows the proposal's central sync mechanism assumes exactly the trusted-channel model this codebase's own recent, hard-won security work proved false for this app's threat model — and the concrete adversarial history of that work (TOMB-1/TOMB-2, still open on the security branch) is direct, first-party proof that this problem is genuinely hard even when tackled carefully, not a corner that can be waved off.

**Salvageable pieces, scoped down and done separately, not as a package:**
- Finish and merge the M4 lazy-EPUB fix already in flight on `security-fixes/tombstone-trust`/its `wp-c` work (directive 2) — real, bounded, already mostly written.
- Finish, adversarially re-review, and merge the Ed25519 tombstone-signing branch itself (fix TOMB-1/TOMB-2 first) — this is the correct foundation *if* BYOS sync payloads are ever extended beyond metadata.
- If podfic/large-payload offload is wanted later, model it as a straightforward extension of the already-shipped `hasEPUB`/`EPUBPreservationStatus` state machine (a `payloadLocation` field, not a rearchitecture) with iCloud's Ubiquitous Container as the only backend (matches the platforms actually shipped today) — Google Drive OAuth and WebDAV are separate, much larger product decisions that deserve their own proposal, not a rider on a storage-tiering change.

No code was changed as part of this review.

# Part 2: Review of the Revised Proposal (JSON Delta Merge, not CRDT)

The owner submitted a revised proposal that keeps the same Sync Hub / Shared Core / iCloud-Google Drive-WebDAV structure but replaces the CRDT engine with application-level JSON delta merging on top of the existing manifest+tombstone format, and asks specifically to check the `hig-review` and `android` branches. This section verifies every factual claim in that revision against real code and answers its four directives. It supersedes Part 1's bottom-line recommendation; Part 1's gap analysis (CRDT-vs-tombstone-trust) is re-tested below against what actually changed.

## Branch landscape this revision needs, clarified

Neither this worktree's `main` (`c878804`) nor `android/mupdf-engine` (`cbbb804`) is the branch this revision is describing. There are three relevant, un-merged tiers, confirmed by `git merge-base --is-ancestor` and `git log --oneline main..<branch>`:

- **`main`** (`c878804`) — `KudosBackupManifest.currentVersion = 7` (`Services/KudosBackup.swift:174`). No `ReadingAnnotation` model exists at all (`grep -rl Annotation kudos-ao3-reader` returns nothing). No Ed25519 signing.
- **`hig-review`** (`c241d2f`, worktree `/Users/cidy02/Documents/AO3_App_OpenSource/.claude/worktrees/hig-review-reference`) — **not an ancestor of `main`**, 575 commits ahead of it. This is where `manifest.json` actually became v8: it adds `@Model final class ReadingAnnotation` (`Models.swift:778`) and a sixth tombstone case, `readingAnnotation` (`Models.swift:50`), with a matching `SyncTombstones.recordDeletion(of: ReadingAnnotation...)` overload (`Services/PersistenceSync.swift:350-359`). No Ed25519 signing yet.
- **`security-fixes/tombstone-trust`** (`1369d4d`) — branches *from* `hig-review` (`git merge-base hig-review security-fixes/tombstone-trust` = `hig-review`'s own tip), adding the Ed25519 signing layer from Part 1 on top of `hig-review`'s v8 schema. This is where `signerPublicKey`/`signature` fields and `currentVersion = 8` with signing actually coexist.

So "manifest.json (v8)" is a real, correct citation — **but only against `hig-review`, not `main`**. On `main`, the format is v7 and lacks the annotation tombstone type entirely. This matters because it means "the existing signed-tombstone mechanism" the revision leans on for its trust story is not one thing sitting in the repo today — it's two separate, both-unmerged branches, stacked on top of each other, and the *second* one (the actual signing) is the one carrying the two open, self-identified forgery holes (TOMB-1/TOMB-2) documented in Part 1.

## Directive 1 — Tombstone robustness: is every critical deletion tombstoned?

**No — verified gap, not proposal error.** `SyncTombstones` (`Services/PersistenceSync.swift:311-376`, same on `main` and `hig-review`) has `recordDeletion` overloads for: `SavedWork`, `WorkCollection`, `ReadingQueue`, `ReadingQueueMembership`, and (on `hig-review` only) `ReadingAnnotation`, plus a same-file helper for collection-membership removal. There is **no overload for `Bookmark`** (the saved-AO3-link model, `Models.swift:498`) or **`CustomFont`**, and no corresponding `SyncTombstoneRecordType` case for either. Confirmed concretely for fonts: `SettingsView.swift`'s `deleteCustomFonts(at:)` (`hig-review:kudos-ao3-reader/Settings/SettingsView.swift:599-609`) does `try? FileManager.default.removeItem(at: font.fileURL); context.delete(font)` with no tombstone call anywhere nearby or in the call chain. A stale `.kudosbackup`/folder-sync snapshot from before a font deletion would silently re-insert that `CustomFont` row on the next restore (the font *file* would be gone, so this manifests as a dangling/broken font reference, not full resurrection — lower severity than a work coming back, but a real, unhandled case). This is a legitimate finding for whoever picks up "finish tombstone coverage," independent of whether the sync-mechanism proposal itself is adopted.

## Directive 2 — Hydration state: does `epubPreservationStatusRaw` cover cloud states?

**No, and the revision correctly identifies this as needed new work rather than overclaiming it already exists** (unlike some of Part 1's original proposal). `EPUBPreservationStatus` (`Models.swift:4-11`, identical on `main` and `hig-review`) is `notPreserved / queued / preserving / preserved / failed / missingFile` — all of these describe the *local-disk* download-and-protect lifecycle (this is the Reading Queue "preserve permanently" feature, driven by `ReadingQueueService.swift`), not cloud offload/rehydration. There is no `downloading` (from cloud), `uploadingToCloud`, or per-provider case anywhere in this enum on any branch. Adding those states is exactly the kind of bounded, additive enum-extension work Part 1's directive 2 already scoped out — real but contained, since `epubPreservationStatusRaw` is a raw string persisted with a documented "unknown values decode safely" contract (`Models.swift` comment: *"Stored as raw strings so future app versions and other platforms can decode unknown/default values safely"*), so adding cases is schema-safe. The harder part, as in Part 1, is the ~10 UI/service call sites that currently treat "EPUB absent" as one case and would need a second branch for "absent because it's in the cloud, not because it was never downloaded."

## Directive 3 — SwiftUI/Shared-Core decoupling via a KMP/Rust JSON parser

**Same answer as Part 1 directive 1, restated for the narrower "JSON parser" framing — still not a small change.** Swapping *only* the JSON-parsing/merge layer to a Shared Core while keeping SwiftData/Room as the local store (which is what this revision, unlike the original, actually proposes — §3 no longer says "migrate away from SwiftData/Room") is meaningfully smaller than Part 1's full persistence-layer rewrite, because `@Query`/`#Predicate` observation stays untouched. What the Shared Core would still have to reimplement or wrap, correctly, on both platforms: the `TombstoneIndex` resolution rules (`KudosBackup.swift`'s private `TombstoneIndex` struct — six different lookup tables keyed by ID/AO3-work-ID/canonical-URL, `KudosBackup.swift:1401`+), the LWW-per-field merge semantics for works/collections/queues/memberships, the `BackupImportMode` (`.reconcile` vs `.merge` vs `.replace`) branching, and (if it's meant to be trust-checked at all — see below) the signing/verification logic. That's the actual complexity of this codebase's sync behavior; it was never the JSON parsing itself. A "Shared Core" here is realistically a port of `KudosBackup.swift`'s restore logic (rather than a rewrite of the whole data layer), which is a smaller, more honest scope than the original proposal — but the revision doesn't name that scope explicitly, so it's not clear the author has priced it correctly either.

## Directive 4 — Google Drive OAuth without a bloated SDK

**Unchanged from Part 1: still no OAuth code anywhere in this codebase on any branch checked** (`main`, `hig-review`, `android/mupdf-engine` all re-checked). `ASWebAuthenticationSession` (iOS) and Custom Tabs + a hand-rolled PKCE exchange (Android) remain the right minimal-dependency choices in the abstract, but this is 100% new infrastructure with a new credential-storage and consent surface, not a refactor of anything existing.

## Does this revision close the CRDT-vs-tombstone-trust gap? — **No, and the proposal text itself shows why.**

This is the question that matters most, and it's answered by reading §4 of the revised proposal literally, not by assuming good intent from the word "reuse."

**What §4 actually says the resolution step does:** *"downloads the Delta, compares the `lastModifiedAt` timestamps of the incoming objects against its local database, processes any new `tombstones` to delete local records, and updates the UI."* That's the entire described mechanism. There is no mention anywhere in the revised document — not in §2, §4, or the Sync Hub sections — of `signerPublicKey`, `signature`, a trust store, `TombstoneSigning.verify`, or any adversarial-write assumption at all. "Processes any new tombstones to delete local records" describes **unconditional trust of every tombstone in the delta file** — which is not merely "the same gap as the original CRDT proposal," it is a **regression relative to the codebase's own already-shipped Phase 1 behavior**. Confirmed on `main`, unsigned incoming tombstones are still explicitly *dropped*, not acted on — `KudosBackup.swift`'s restore path only inserts an incoming tombstone after a dedup-key check today (no signature check yet on `main`, since Phase 2 hasn't landed there — but the shape of the logic is "insert into local store and let it suppress," which is Phase-1-safe because there's no attacker-controlled trust decision embedded yet, it's a straightforward last-write-wins compare against the *local* device's own prior state where the file must be legitimately connected). Once you add "act on tombstones from a file you don't control" as this revision's §4 describes, without a verify+trust gate in front of it, you've built something an attacker can point at directly: drop a `.kudosbackup`-shaped delta file with a fabricated tombstone for any `recordID` into the sync folder, and by the revision's own described mechanism it gets processed and the local record gets deleted — no forged signature even required, because none is checked.

**Where the actual verify+trust code lives, and why "reuse" doesn't reach it as described:** the real gate — `TombstoneSigning.shouldAdopt(archived, defaults:)` gating the insert in `KudosBackup.swift:1256` (`security-fixes/tombstone-trust:1369d4d`), and the mirrored `TombstoneSigning.verify(incoming)` + `TombstoneSigning.isTrustedSigner(...)` checks in Android's `BackupMergeService.kt` (same branch) — exists **only on `security-fixes/tombstone-trust`**, two branches removed from where this revision is scoped (`hig-review`/`android`), and, per Part 1's findings, **still has two open, unfixed forgery holes at that branch's own final commit** (TOMB-1: the field that actually authorizes suppression, `lastModifiedAt`, isn't in the signed payload; TOMB-2: Android's adopt loop keys on an unsigned `id` field, letting a forged entry silently delete an unrelated local tombstone). If this revision's Shared Core is meant to route through that exact mechanism, the revision needed to say so and account for those two open findings; it doesn't mention either. As written, the revision describes a JSON-delta mechanism that is **less safe than Phase 1, and doesn't reach Phase 2 at all** — the encoding format changed (delta file vs. full CRDT changeset), but the actual gap Part 1 identified — an attacker with sync-folder write access can author a file that gets trusted and acted on — is fully intact, arguably widened, because the description drops even Phase 1's "unsigned still drops" discipline.

There's a second, smaller new risk this revision introduces that CRDT-vs-full-manifest didn't have: **delta semantics on a plain file store.** iCloud/Drive/WebDAV give you files, not an ordered event log. Today's `FolderSyncService.swift` sync-up/down writes and reads one whole coordinated file and relies on `NSFileVersion.unresolvedConflictVersionsOfItem` to fold concurrent edits (`foldFileProviderConflicts`, `FolderSyncService.swift:287-311`) — that's why the format is "ship full current state," not "ship a delta": deltas need stable ordering, replay-idempotency, and garbage collection that a bag of files in a Drive folder doesn't give you for free, and the revision doesn't describe any of that (delta file naming, retention, or what happens when two devices' deltas race on write). This is a solvable problem, but it's additional, undiscussed complexity relative to what already works.

## Updated overall recommendation (across both proposal versions)

**Still reject the Sync Hub / multi-cloud-backend architecture as a package, in both versions.** The revision is a real improvement in honesty about the *storage engine* (dropping "migrate off SwiftData/Room," dropping the CRDT-engine dependency) and its factual citations against the codebase are accurate. But the one property that made Part 1 unacceptable — a sync mechanism that doesn't route attacker-controlled input through the trust check this codebase's own security work spent weeks establishing — is **still true of the revision**, and is arguably worse as literally described, because the revision's plain-language mechanism (§4) reads as strictly more permissive than even this codebase's current, already-shipped Phase-1-only behavior on `main`.

Before any version of this proposal is actionable:
1. **Land `hig-review` and `security-fixes/tombstone-trust` into `main` first**, independent of this proposal — they're prerequisites either way (annotation model, v8 manifest, signing), and the signing branch needs its TOMB-1/TOMB-2 holes closed and re-reviewed before anything is built on top of it, sync-hub or not.
2. **Any revision of this proposal must explicitly specify** that its delta/resolution mechanism routes every incoming tombstone (and, if metadata deltas can also carry authorization-bearing state, every incoming metadata write) through `TombstoneSigning.verify` + trust-store membership before it's acted on — not just cite the existence of signed tombstones as a reason a CRDT library is unnecessary. "We already have signed tombstones so we don't need a CRDT" is true as an engineering-complexity argument and false as a security argument unless the new delta path actually calls the verify function.
3. Directive-1's font/bookmark tombstone gap and directive 2's missing cloud hydration states are legitimate, bounded follow-up work independent of the Sync Hub decision — worth doing regardless of which (if any) proposal version is adopted.
4. The three-cloud-backend surface (iCloud + Google Drive OAuth + WebDAV) and the cross-hub migration flow from Part 1's §6 remain unaddressed by this revision (it keeps the same Sync Hub structure verbatim) and are still a much larger scope commitment than the "storage constraints" problem in §2 actually requires — that assessment from Part 1 stands unchanged.

No code was changed as part of this review.
